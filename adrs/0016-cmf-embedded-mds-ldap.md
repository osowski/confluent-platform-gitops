# 16. CMF Embedded MDS with LDAP

Date: 2026-09-16

## Status

Accepted

## Context

Epic #408 needs CMF's authorization/login story on `flink-demo-rbac` to be
LDAP-backed instead of Keycloak. The epic's first attempt (#412) tried to
route CMF's authorization leg through the external, Kafka broker-hosted
MDS via mTLS (`cmf.authorization.mdsRestConfig.authentication.type: mtls`),
since that leg has no LDAP/bearer option. Live verification found this
approach forced MDS's single REST listener onto HTTPS-only with client
certs required, breaking `erp`/`sr`/`c3`'s already-closed, already-verified
plain-HTTP bearer flows from #411, and CMF's own separate login leg — a
much bigger blast radius than the issue's stated CMF-only scope. #412 was
closed and its live changes fully reverted (see ADR-0015, now superseded
by this ADR).

CMF has a dedicated, purpose-built alternative:
[embedded MDS](https://docs.confluent.io/cp-flink/current/installation/embedded-mds.html).
CMF runs a second, self-contained MDS instance inside its own process,
authenticates directly against an LDAP directory, and authorizes
Flink/CMF resources locally — no external broker-hosted MDS, no mTLS, no
`mdsRestConfig` at all.

## Decision

Enable `cmf.mds.enabled: true` with `user-store: LDAP`, binding to the
existing OpenLDAP directory (#409) via the same `uid=mds` read-only search
identity Kafka's own broker-hosted MDS already uses (not a new dedicated
identity — this bind credential isn't a Kafka RBAC principal, just
directory search access). `cmf.authorization.authority: cmf` replaces
`cp-mds`/`mdsRestConfig` entirely. A new, dedicated RSA key pair (distinct
from the Kafka broker's own `mds-token` secret) signs the embedded MDS's
own JWTs, generated by a `Job` mirroring the existing `mds-keygen`
pattern.

This is architecturally independent of Kafka's own broker-hosted MDS
(#410/#411, untouched) — two separate authorization surfaces (Kafka/CP
resources vs. CMF/Flink resources) sharing one LDAP directory as their
common identity source, but with no shared state or coupling between the
two MDS instances.

`LDAP_WITH_OAUTH` (adding OIDC SSO alongside LDAP) is a secondary,
additive goal on the same configuration, not a separate architecture -
implemented as a follow-on task once the primary LDAP path is
live-verified.

## Consequences

**Positive.** Drastically simpler than the mTLS approach: no CA, no
cert-manager, no TLS-listener coexistence problem, no blast radius onto
already-closed work. CMF's authorization/login story is now fully
self-contained and reuses proven-working LDAP connection details instead
of inventing new PKI.

**Negative.** A second, independent MDS instance (and independent
super-user list, independent role-binding store) now exists alongside
Kafka's broker-hosted MDS — anyone administering RBAC on this cluster
must remember which of the two systems governs which resource type.
`C3` (Control Center) is explicitly unsupported with the embedded MDS per
the doc — this cluster's Control Center continues authorizing against the
Kafka broker-hosted MDS only, unaffected by this change.
