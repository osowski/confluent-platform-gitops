# 26. CMF AI Functions Set Up in the Applications That Own the Environments

Date: 2026-11-20

## Status

Accepted. Tracked in [#575](https://github.com/osowski/confluent-platform-gitops/issues/575) (`default`) and [#576](https://github.com/osowski/confluent-platform-gitops/issues/576) (`colors-env`, `shapes-env`).

## Context

`AI_FORECAST` and `AI_DETECT_ANOMALIES` are CMF preview functions. A Flink environment can run them once three things are in place:

- the function JAR is uploaded as an artifact in that environment;
- both functions are registered in the environment's catalog (`_env_<env>`) with `CREATE FUNCTION ... USING JAR 'cmf://<env>/ai-functions.jar'`;
- the environment's statement defaults carry `ai.models.<model>.endpoint` for each model server.

The standard environments are `default` (owned by `flink-resources`), and `colors-env` and `shapes-env` (owned by `colors-and-shapes`). Facts that shape the decision:

- CFK has no CRD for artifacts. Upload is `POST /cmf/api/v1/environments/<env>/artifacts` only, and a second upload under the same name fails.
- The `FlinkEnvironment` CRD has `spec.statementDefaults`, but CFK 0.1718.99 does not send it to CMF, on create or on any later edit. Verified live on `flink-demo-rbac` through a logging proxy in front of CMF: the stored CR keeps the field, the request CFK posts carries only `flinkApplicationDefaults`, `kubernetesNamespace` and `metadata`, and CMF reports null for both `interactive` and `detached`. Not tested on other CFK versions.
- CMF has no PUT for environments. `POST /cmf/api/v1/environments` is createOrUpdate, and an update replaces every default it omits (`flinkApplicationDefaults`, `computePoolDefaults`, statement defaults).
- A DDL-only `FlinkStatement` settles to COMPLETED, a re-apply of an unchanged one is a no-op, and deleting and recreating it works. Verified live on `kind-flink-demo`.
- No workload here references another workload's Kustomize files, and each Application has to stay syncable alone.

## Decision

- **Each Application sets up the environments it owns.** `flink-resources` sets up `default`, and `colors-and-shapes` sets up `colors-env` and `shapes-env` with the same script and one Job per environment (`ai-functions-setup-colors`, `ai-functions-setup-shapes`, wave 82, after the FlinkApplications at 80; `CREATE FUNCTION` statements at wave 85 in `flink-colors` and `flink-shapes`). A cluster without `colors-and-shapes` is unaffected.
- **The `ttm` model server is deployed by the same `flink-resources` Application** (wave 90), as Service `model-server-ttm` at `http://model-server-ttm.flink.svc.cluster.local:8080/v1/forecast`. That is the URL the setup Job writes into the environment.
- **Statement defaults are written by the setup Job through the CMF API**, not by the `FlinkEnvironment` CR. The CR carries no `statementDefaults`. The Job reads the environment, sets only the `ai.models.*` keys in the `interactive` and `detached` blocks, and posts the whole environment back through createOrUpdate, leaving every other default as read. The Job owns every `ai.models.<name>.endpoint` key in those blocks: a key for a model not in its `MODEL_ENDPOINTS`, including one added by hand, is removed on the next sync. It skips the post when the keys already hold the target values.
- **Artifact upload is an idempotent Argo CD hook Job** (`Sync`, `BeforeHookCreation`, wave 52 in `flink-resources`, with a 30-minute `activeDeadlineSeconds`). It waits for CFK to create the environment in CMF, then reads `ai-functions.jar`: when it is missing, the Job downloads the JAR, verifies its pinned sha256 and uploads it; when it exists, its latest version must be `READY` with the pinned sha256, or the Job fails without replacing it. The pinned `python:3.12-alpine` image runs a standard-library-only script from a ConfigMap generated from `ai_functions_setup.py`. The Job runs in the `flink` namespace on every cluster. On the three OAuth clusters a component patch adds a client-credentials token fetch from the `cfk-cmf-oauth-client` Secret.
- **`CREATE FUNCTION` stays a `FlinkStatement`.** `create-ai-forecast` and `create-ai-detect-anomalies` (wave 55, after the compute pool and the setup Job) use `IF NOT EXISTS`. The live gate on the fallback conditions passed, so no statement-submitting code goes in the Job.
- **The script is duplicated between the two Applications.** Each Application carries its own copy so it can sync alone. Both Applications deploy into the `flink` namespace, so `colors-and-shapes` names its generated ConfigMap `ai-functions-setup-script-cs` to keep it apart from `flink-resources`' `ai-functions-setup-script`.

## Alternatives Considered

- **All AI setup in `flink-resources`.** One copy of the script, but it would target environments owned by an Application that syncs later, and it breaks on a cluster without `colors-and-shapes`.
- **A new `ai-functions` Application.** Model servers and function setup belong with the environments and servers they extend.
- **`statementDefaults` on the `FlinkEnvironment` CR.** Declarative and the first choice, but CFK does not send it to CMF at creation, so it has no effect.
- **A blind environment update carrying only the AI keys.** Rejected: the update replaces `flinkApplicationDefaults`, including the Prometheus reporter and Schema Registry OAuth settings.
- **`CREATE FUNCTION` inside the Job.** The fallback; not needed.

## Consequences

- **The setup runs on Argo CD sync and does not repair itself.** If CMF loses its state, the artifact, functions and defaults are not restored until the cluster is rebuilt from zero.
- **A change to either `CREATE FUNCTION` statement is a new CR with a versioned name,** because `spec.statement` is immutable once running. With `IF NOT EXISTS` a new CR is a no-op while the function is still registered, so a changed class or JAR also needs a `DROP FUNCTION` first.
- **The JAR is pinned.** Moving to a later JAR needs a new URL and checksum, a new artifact version, and a re-registration; it is not handled automatically. The Job accepts an existing artifact only when its latest version is `READY` with the pinned sha256, and never replaces one: after a pin change, or when CMF reports a phase that does not clear by itself such as `FILE_MISSING`, the Job fails with the observed and expected values until the functions and the artifact are removed by hand (see the teardown bullet below). `UPLOADING` and `STORE_UNREACHABLE` can clear by themselves, so the Job retries them.
- **Exit codes.** The script exits 2 for errors a retry cannot fix, and each Job's `podFailurePolicy` fails the Job at once on it: a JAR sha256 mismatch (including a `200` with the wrong body, such as a proxy page), a missing or malformed variable, an OAuth file without its `clientId` or `clientSecret` line, an environment update body that fails its safety check, HTTP 401 or 403 from the token endpoint, and an existing artifact whose phase or checksum does not match. Everything else exits 1 and is retried up to `backoffLimit`: timeouts, refused connections, 5xx, and every other HTTP error from CMF or the JAR host, including CMF's 401 and 403 (CMF answers 401 for an authorization denial too, so a role binding that is not effective yet looks like a bad token) and a 404 on `JAR_URL`. Failed CMF calls log CMF's error message, and the failed Job stays until the next sync replaces it.
- **On the RBAC clusters the Job's principal is `cmf`.** According to the Confluent access-control role table ([access-control](https://docs.confluent.io/cp-flink/current/configure/access-control.html)), the `cmf` principal's `ClusterAdmin` binding on `default` covers artifacts and statements. The `cmf-clusteradmin-colors-env` and `cmf-clusteradmin-shapes-env` bindings give it the same role on `colors-env` and `shapes-env`; by the same table they cover artifacts and statements there too (verified live on `flink-demo-rbac`: the Jobs uploaded the artifact and the `CREATE FUNCTION` statements, `AI_FORECAST` and `AI_DETECT_ANOMALIES` ran in both environments).
- **The Job runs after the compute pool and before the `CREATE FUNCTION` statements.** The environment (wave 5) comes first and the pool needs neither the statement defaults nor the artifact, so topics, schemas, catalog, database and pool sync before the Job and are unaffected by it. In `flink-resources` the Job is at wave 52 and the statements at 55, which need the artifact. In `colors-and-shapes` the Jobs are at wave 82 and the statements at 85, after the FlinkApplications (80), so the Job waits for them to be Healthy. Topics, schemas, catalog, database, pools, the existing `colors-sql-enrich` and `shapes-sql-enrich` statements (70) and the FlinkApplications are applied before the AI setup. A Job that fails (`backoffLimit: 6`) or runs past its deadline fails the sync at wave 82, and only the `CREATE FUNCTION` statements (85) wait for it to succeed. `activeDeadlineSeconds: 1800` bounds each Job.
- **A CFK reconcile of the `default` FlinkEnvironment CR clears the statement defaults.** A spec change to the CR makes CFK post the environment to CMF without `statementDefaults`, which empties the `ai.models.*` keys (verified live: after a CR edit, CMF reported `statementDefaults` as null for both `interactive` and `detached`). Restarting the CFK operator alone does not trigger a reconcile. Until the next Argo CD sync, new statements that call a model fail with `has no model server URL in this environment`; the sync's Job restores the keys (verified live). A hand edit of the CR therefore needs a sync afterwards. The same holds for `colors-env` and `shapes-env`: every environment post from CFK omits `statementDefaults` (verified by request capture on a throwaway environment, not by editing those two); there the sync is the `colors-and-shapes` Application's.
- **Deleting an environment that has the AI functions set up (`default`, `colors-env`, `shapes-env`) needs a manual teardown first.** CMF refuses to delete an environment that still holds an artifact (`Environment '<env>' cannot be deleted because it has 1 artifact ('ai-functions.jar') that must be deleted first.`) or a registered function (`... it has 2 functions ('ai_detect_anomalies', 'ai_forecast') in the default catalog database that must be deleted first.`); the CR then stays in CFK state `ERROR` with its finalizer, and the Application stays in Deleting. The order is: drop both functions with `DROP FUNCTION IF EXISTS` statements, created as FlinkStatement CRs in the environment's namespace (`flink`, `flink-colors` or `flink-shapes`) on its live compute pool (`pool`, `colors-pool` or `shapes-pool`; catalog `_env_<env>`, database `default`); wait for both to reach `COMPLETED`; delete those two statements, because CMF also refuses to delete an environment that still holds any statement; then `DELETE /cmf/api/v1/environments/<env>/artifacts/ai-functions.jar` (on the OAuth clusters with a bearer token for the `cmf` client from the `cfk-cmf-oauth-client` Secret, as the Job uses); then delete the environment CR or the Application. This must happen before the Application or its pool is deleted: deleting the `CREATE FUNCTION` statement CRs does not drop the functions, and the pool (wave 50 in `flink-resources`, 60 in `colors-and-shapes`) is deleted before the environment (wave 5). A direct delete of an environment CR that has a Kafka catalog also waits on its `FlinkKafkaDatabase` and `FlinkKafkaCatalog` CRs, because CFK cascade-deletes the secret mapping the catalog references; delete the database, then the catalog (observed on `shapes-env`). Dropping the functions and deleting the artifact (not the environment or the Application), then deleting the two `create-ai-*` FlinkStatement CRs and syncing, recovers from a setup Job that fails on an existing artifact that is not `READY` or has another checksum (not verified live). Verified live: `DROP FUNCTION` on `default` and `shapes-env`; `DROP FUNCTION IF EXISTS` completing on a missing function, where the plain form ends `FAILED`; the artifact `GET` and `DELETE` and the token fetch through port-forwards on `flink-demo-rbac`; the whole `shapes-env` teardown.
- **The Job downloads the JAR from `packages.confluent.io`** (`io.confluent.flink:cp-flink-ai-detect-anomalies:1.0.0`), so its pod needs egress to that host. Where egress is restricted the Job retries (exit 1) until `activeDeadlineSeconds`.
- **A change to only a Job does not mark its Application OutOfSync,** because hook resources are not diffed. The `flink-resources` and `colors-and-shapes` Applications are manual-sync on every cluster, so a changed `MODEL_ENDPOINTS` or `JAR_SHA256` needs a manual sync to run the Job.
- **There are two copies of the script to keep in step.** A test compares them byte for byte.
