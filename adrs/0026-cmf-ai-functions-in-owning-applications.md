# 26. CMF AI Functions Set Up in the Applications That Own the Environments

Date: 2026-11-20

## Status

Accepted. Tracked in [#575](https://github.com/osowski/confluent-platform-gitops/issues/575) (`default`) and [#576](https://github.com/osowski/confluent-platform-gitops/issues/576) (`colors-env`, `shapes-env`).

## Context

`AI_FORECAST` and `AI_DETECT_ANOMALIES` are CMF preview functions. A Flink environment can run them once three things are in place:

- the function JAR is uploaded as an artifact in that environment;
- both functions are registered in the environment's catalog (`_env_<env>`) with `CREATE FUNCTION ... USING JAR 'cmf://<env>/ai-functions.jar'`;
- the environment's statement defaults carry `ai.models.<model>.endpoint` for each model server.

The standard environments are `default` (owned by `flink-resources`), and `colors-env` and `shapes-env` (owned by `colors-and-shapes`). Facts that shape the decision:

- CFK has no CRD for artifacts. Upload is `POST /cmf/api/v1/environments/<env>/artifacts` only, and a second upload under the same name fails.
- The `FlinkEnvironment` CRD has `spec.statementDefaults`, but CFK 0.1718.99 does not send it to CMF, on create or on any later edit. Verified live on `flink-demo-rbac` through a logging proxy in front of CMF: the stored CR keeps the field, the request CFK posts carries only `flinkApplicationDefaults`, `kubernetesNamespace` and `metadata`, and CMF reports null for both `interactive` and `detached`. Not tested on other CFK versions.
- CMF has no PUT for environments. `POST /cmf/api/v1/environments` is createOrUpdate, and an update replaces every default it omits (`flinkApplicationDefaults`, `computePoolDefaults`, statement defaults).
- A DDL-only `FlinkStatement` settles to COMPLETED, a re-apply of an unchanged one is a no-op, and deleting and recreating it works. Verified live on `kind-flink-demo`.
- No workload here references another workload's Kustomize files, and each Application has to stay syncable alone.

## Decision

- **Each Application sets up the environments it owns.** `flink-resources` sets up `default`, and `colors-and-shapes` sets up `colors-env` and `shapes-env` with the same script and one Job per environment (`ai-functions-setup-colors`, `ai-functions-setup-shapes`, wave 62, after the pools at 60; `CREATE FUNCTION` statements at wave 65 in `flink-colors` and `flink-shapes`). A cluster without `colors-and-shapes` is unaffected.
- **The `ttm` model server is deployed by the same `flink-resources` Application** (wave 90), as Service `model-server-ttm` at `http://model-server-ttm.flink.svc.cluster.local:8080/v1/forecast`. That is the URL the setup Job writes into the environment.
- **Statement defaults are written by the setup Job through the CMF API**, not by the `FlinkEnvironment` CR. The CR carries no `statementDefaults`. The Job reads the environment, sets only the `ai.models.*` keys in the `interactive` and `detached` blocks, and posts the whole environment back through createOrUpdate, leaving every other default as read. The Job owns every `ai.models.<name>.endpoint` key in those blocks: a key for a model not in its `MODEL_ENDPOINTS`, including one added by hand, is removed on the next sync. It skips the post when the keys already hold the target values.
- **Artifact upload is an idempotent Argo CD hook Job** (`Sync`, `BeforeHookCreation`, wave 52 in `flink-resources`, with a 30-minute `activeDeadlineSeconds`). It waits for CFK to create the environment in CMF, checks whether `ai-functions.jar` exists, and only otherwise downloads the JAR, verifies its pinned sha256 and uploads it. The pinned `python:3.12-alpine` image runs a standard-library-only script from a ConfigMap generated from `ai_functions_setup.py`. The Job runs in the `flink` namespace on every cluster. On the three OAuth clusters a component patch adds a client-credentials token fetch from the `cfk-cmf-oauth-client` Secret.
- **`CREATE FUNCTION` stays a `FlinkStatement`.** `create-ai-forecast` and `create-ai-detect-anomalies` (wave 55, after the compute pool and the setup Job) use `IF NOT EXISTS`. The live gate on the fallback conditions passed, so no statement-submitting code goes in the Job.
- **The script is duplicated between the two Applications.** Each Application carries its own copy so it can sync alone. Both Applications deploy into the `flink` namespace, so `colors-and-shapes` names its generated ConfigMap `ai-functions-setup-script-cs` to keep it apart from `flink-resources`' `ai-functions-setup-script`.

## Alternatives Considered

- **All AI setup in `flink-resources`.** One copy of the script, but it would target environments owned by an Application that syncs later, and it breaks on a cluster without `colors-and-shapes`.
- **A new `ai-functions` Application.** Model servers and function setup belong with the environments and servers they extend.
- **`statementDefaults` on the `FlinkEnvironment` CR.** Declarative and the first choice, but CFK does not send it to CMF at creation, so it has no effect.
- **A blind environment update carrying only the AI keys.** Rejected: the update replaces `flinkApplicationDefaults`, including the Prometheus reporter and Schema Registry OAuth settings.
- **`CREATE FUNCTION` inside the Job.** The fallback; not needed.

## Consequences

- **The setup runs on Argo CD sync and does not repair itself.** If CMF loses its state, the artifact, functions and defaults are not restored until the cluster is rebuilt from zero.
- **A change to either `CREATE FUNCTION` statement is a new CR with a versioned name,** because `spec.statement` is immutable once running. With `IF NOT EXISTS` a new CR is a no-op while the function is still registered, so a changed class or JAR also needs a `DROP FUNCTION` first.
- **The JAR is pinned.** Moving to a later JAR needs a new URL and checksum, a new artifact version, and a re-registration; it is not handled automatically. The Job accepts an existing artifact only when its latest version is `READY` with the pinned sha256, and never replaces one: after a pin change, or when CMF reports a phase that does not clear by itself such as `FILE_MISSING`, the Job fails with the observed and expected values until the functions and the artifact are removed by hand. `UPLOADING` and `STORE_UNREACHABLE` can clear by themselves, so the Job retries them.
- **Errors a retry cannot fix fail the Job at once.** The script exits 2 for a pin mismatch, an artifact in a phase that does not clear by itself, a missing or malformed variable, an OAuth file without its `clientId` or `clientSecret` line, and HTTP 401 or 403; each Job's `podFailurePolicy` turns that into an immediate Job failure instead of `backoffLimit` retries. Failed CMF calls log CMF's error message, and the failed Job stays until the next sync replaces it.
- **On the RBAC clusters the Job's principal is `cmf`.** According to the Confluent access-control role table ([access-control](https://docs.confluent.io/cp-flink/current/configure/access-control.html)), the `cmf` principal's `ClusterAdmin` binding on `default` covers artifacts and statements. The `cmf-clusteradmin-colors-env` and `cmf-clusteradmin-shapes-env` bindings give it the same role on `colors-env` and `shapes-env`; by the same table they cover artifacts and statements there too (verified live on `flink-demo-rbac`: the Jobs uploaded the artifact and the `CREATE FUNCTION` statements, `AI_FORECAST` and `AI_DETECT_ANOMALIES` ran in both environments).
- **The Job runs after the compute pool and before the `CREATE FUNCTION` statements.** The environment (wave 5) comes first and the pool needs neither the statement defaults nor the artifact, so topics, schemas, catalog, database and pool sync before the Job and are unaffected by it. In `flink-resources` the Job is at wave 52 and the statements at 55, which need the artifact. In `colors-and-shapes` the Jobs are at wave 62 and the statements at 65; a Job that fails (`backoffLimit: 6`) or runs past its deadline fails the sync at wave 62, so the `CREATE FUNCTION` statements, the existing `colors-sql-enrich` and `shapes-sql-enrich` statements (70) and the FlinkApplications (80) are not applied until it succeeds. `activeDeadlineSeconds: 1800` bounds each Job.
- **A CFK reconcile of the `default` FlinkEnvironment CR clears the statement defaults.** A spec change to the CR makes CFK post the environment to CMF without `statementDefaults`, which empties the `ai.models.*` keys (verified live: after a CR edit, CMF reported `statementDefaults` as null for both `interactive` and `detached`). Restarting the CFK operator alone does not trigger a reconcile. Until the next Argo CD sync, new statements that call a model fail with `has no model server URL in this environment`; the sync's Job restores the keys (verified live). A hand edit of the CR therefore needs a sync afterwards. The same holds for `colors-env` and `shapes-env`: every environment post from CFK omits `statementDefaults` (verified by request capture on a throwaway environment, not by editing those two); there the sync is the `colors-and-shapes` Application's.
- **Deleting a FlinkEnvironment CR that has the AI functions set up (`default`, `colors-env`, `shapes-env`) needs the functions dropped and the artifact deleted first.** CMF refuses to delete an environment that still holds an artifact (`Environment '<env>' cannot be deleted because it has 1 artifact ('ai-functions.jar') that must be deleted first.`) or a registered function (`... it has 2 functions ('ai_detect_anomalies', 'ai_forecast') in the default catalog database that must be deleted first.`). The CR stays in CFK state `ERROR` with its finalizer until `DELETE /cmf/api/v1/environments/<env>/artifacts/<name>` removes the artifact and a `DROP FUNCTION` statement removes each function. Deleting the `CREATE FUNCTION` statement CRs does not drop the functions, and a `DROP FUNCTION` needs a compute pool, so the drop must run before the Application's resources are deleted: the pool (wave 50 in `flink-resources`, 60 in `colors-and-shapes`) is deleted before the environment (wave 5). The READMEs' teardown sections have the steps. Verified live on `default` and on `shapes-env`. A direct delete of an environment CR that has a Kafka catalog also waits on the catalog and database CRs, because CFK cascade-deletes the secret mapping the catalog references; the `colors-and-shapes` README has the steps.
- **There are two copies of the script to keep in step.** A test compares them byte for byte.
